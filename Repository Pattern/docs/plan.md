# Repository Pattern サンプル実装計画

## 問題と方針

現状の`RepositoryPattern.Console`は.NET 10のコンソールアプリ雛形である。添付メモと`RepositoryPattern_ARC42.md`の仕様に基づき、商品・注文・注文明細を題材に、Repositoryパターンを使わないBad実装と、Repository + Unit of Workを適用したGood実装を同一プロジェクト内に段階的に追加する。

実装では、SQLiteとDapperによる永続化、同一トランザクションを共有するUnit of Work、依存性注入可能な注文サービス、成功・在庫不足・途中失敗の実行例、およびテスト可能な設計を重視する。初学者がGood/Badの差を追跡できるよう、過度な抽象化や不要なプロジェクト分割は避ける。

## 実装ステップ

1. **プロジェクト基盤を整える**
   - `Microsoft.Data.Sqlite`と`Dapper`を追加する。
   - 必要に応じてテストプロジェクトとxUnit関連パッケージを追加する。
   - 名前空間、Nullable、既存の.NET 10設定を確認する。

2. **ドメインエンティティを作成する**
   - `Product`、`Order`、`OrderItem`を作成する。
   - 商品価格・注文合計・明細単価は円単位の整数で扱う。
   - 注文時点の単価を`OrderItem.UnitPrice`へ保持する。

3. **SQLite初期化とスキーマを実装する**
   - `Products`、`Orders`、`OrderItems`テーブルを作成する。
   - 外部キー、必須制約、主キーを定義する。
   - 研修用のサンプル商品を投入する。
   - 初期化処理が研修用であり、既存データを削除し得ることを明示する。

4. **Bad実装を作成する**
   - `OrderService`相当のクラスに接続、SQL、在庫検証、注文登録を直接記述する。
   - Repositoryを使用せず、業務ロジックとSQLite/DapperまたはSQLite APIを密結合させる。
   - トランザクションなしの途中失敗で在庫だけが更新される問題を再現可能にする。
   - Bad実装が推奨設計ではなく比較教材であることをコード・実行表示で明示する。

5. **Repositoryの契約と実装を作成する**
   - `IProductRepository`に商品取得と在庫更新の最小契約を定義する。
   - `IOrderRepository`に注文ヘッダ・明細登録の最小契約を定義する。
   - `ProductRepository`と`OrderRepository`へSQLを集約する。
   - Dapperのパラメータを使用し、SQL文字列をサービス層へ漏らさない。
   - 在庫更新件数を検証し、競合や在庫不足をエラーとして扱えるようにする。

6. **Unit of Workを作成する**
   - `IUnitOfWork`にRepository公開、`Commit`、`Rollback`、破棄の契約を定義する。
   - `UnitOfWork`でSQLite接続を開き、トランザクションを開始する。
   - 全Repositoryへ同じ接続とトランザクションを渡す。
   - 成功時の確定、失敗時の取消、接続・トランザクションの解放を保証する。

7. **Goodの注文サービスを作成する**
   - `OrderService`は注文確定の業務フローだけを担当する。
   - Unit of Workまたはファクトリをコンストラクター注入する。
   - 商品存在、数量の妥当性、在庫を検証してから更新する。
   - 在庫減算、注文登録、明細登録を同一Unit of Workで実行する。
   - 成功時にCommitし、例外時にRollbackして元の例外を再送出する。
   - 空数量、負数、存在しない商品などの入力境界を明示的に扱う。

8. **Composition Rootと実行シナリオを作成する**
   - `Program.cs`で接続文字列と具象依存関係を組み立てる。
   - DB初期化後、Good/Bad双方を実行できる導線を作る。
   - 成功ケース、在庫不足ケース、存在しない商品ケースを表示する。
   - 可能であれば、明細登録失敗を注入してRollback結果を確認する。
   - 実行後に在庫、注文、明細の状態を表示し、Good/Badの差を観察できるようにする。

9. **単体テストを追加する**
   - Goodのサービスが実DBなしで動くようFake Repository/Unit of Workを用意する。
   - 成功時にCommitされ、必要なRepository操作が呼ばれることを検証する。
   - 在庫不足・商品不存在・不正数量で更新されず、Rollbackまたは失敗になることを検証する。
   - 注文登録または明細登録の失敗時にRollbackされ、例外が失われないことを検証する。
   - RepositoryのSQLマッピングとSQLite統合動作は必要最小限の統合テストで確認する。

10. **研修資料とコードの整合性を確認する**
    - ARC42文書の想定ディレクトリ、クラス名、実行フローを実装と一致させる。
    - Good/Bad比較表に、実際に確認できる差分だけを記載する。
    - READMEまたは実行時案内に、実行方法・DB初期化・教材上の注意を追記する。
    - 仕様書の実装チェックリストを更新する。

11. **検証と品質確認を行う**
    - `dotnet restore`、`dotnet build`、対象テストを実行する。
    - Goodの成功・失敗・Rollbackシナリオを実行確認する。
    - `git diff --check`でMarkdownとコードの空白エラーを確認する。
    - `bin`、`obj`、SQLite実行DBなどの生成物がコミット対象に含まれないことを確認する。

## 重要な判断・考慮事項

- DBはSQLiteの単一ファイルとし、外部サービスは導入しない。
- 金額は仕様どおり整数の円単位とする。
- Bad実装は意図的なアンチパターンとして隔離し、本番向けの推奨例と誤認させない。
- Serviceが具象`UnitOfWork`を直接`new`しない構造を優先し、テスト時の差し替えを可能にする。
- トランザクションの境界は1回の注文確定とし、商品・注文・明細の更新を一括して扱う。
- 初期化時のテーブル再作成は研修用に限定し、運用環境向けのマイグレーションとは分けて考える。
- 現在は設計書のみが追加済みで、実装開始時に既存の雛形と設計書の差分を確認してから変更する。
