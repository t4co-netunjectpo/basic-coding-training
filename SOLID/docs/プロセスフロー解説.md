# Goodパターン（`SolidSample.Good`）の振る舞い（実行プロセス）

Goodパターンでは、DI（依存性の注入）**と**ポリモーフィズム（多態性）を活用し、具象クラスではなくインターフェース（抽象）を介してすべてのプロセスが連動するよう設計されています。

---

### 1. 依存関係の組み立て（Composition Root）

プログラムが起動すると、最初にDIコンテナの初期化とインスタンスの依存関係の登録を行います。

* **コードポインタ**: `SolidSample.Good\Program.cs`（11〜32行目付近）
* **プロセスの振る舞い**:
  1. `new ServiceCollection()` でDIコンテナの元となるコレクションを生成します。
  2. `ISalesRepository` に対して `InMemorySalesRepository` を登録します（DataAccess）。
  3. `IReportFormatter` に対して `CsvFormatter`, `JsonFormatter`, `MarkdownFormatter` の3つを複数登録（コレクションとして保持）します（Formatters）。
  4. 出力用の各種インターフェース（`IFileWriter`, `IEmailSender`, `IConsoleWriter`）にそれぞれの具象クラスを登録します（Output）。
  5. 最後に調整役となる `ReportService` を登録し、`services.BuildServiceProvider()` を実行してインスタンスを解決可能な状態（DIコンテナ）にします。

### 2. サービスの解決（Resolve）

構築したDIコンテナから、実際に業務ロジックを呼び出すためのエントリーポイントとなるサービスを取得します。

* **コードポインタ**: `SolidSample.Good\Program.cs`（35行目付近）
* **プロセスの振る舞い**:
  * `serviceProvider.GetRequiredService<ReportService>()` を呼び出します。
  * このとき、コンテナは `ReportService` のコンストラクタ（`SolidSample.Good\Services\ReportService.cs` の17行目）に必要なすべての依存関係（`ISalesRepository`, `IEnumerable<IReportFormatter>`, 各種Writer/Sender）の具象インスタンスを自動的に注入（コンストラクタインジェクション）します。

### 3. ユースケースの実行（例：CSV to Console の場合）

`Program.cs` からサービスメソッドが呼び出され、実際の業務フローが始まります。ここでは例として `service.PrintToConsole("CSV");` が実行された際の内部プロセスを追います。

#### 3.1. サービスの受付

* **コードポインタ**: `SolidSample.Good\Services\ReportService.cs` の `PrintToConsole(string formatName)` メソッド
* **プロセスの振る舞い**:
  * 引数として `"CSV"` を受け取り、内部のプライベートメソッドである `BuildReport(formatName)` を呼び出します。

#### 3.2. データの取得（DataAccess層の呼び出し）

* **コードポインタ**: `SolidSample.Good\Services\ReportService.cs` 内の `BuildReport` メソッド -> `SolidSample.Good\DataAccess\InMemorySalesRepository.cs` の `GetAll()`
* **プロセスの振る舞い**:
  * `ReportService` は、注入された抽象である `_repository.GetAll()` を呼び出します。
  * 実際には `InMemorySalesRepository` が動作し、インメモリで定義された `SalesRecord` のリスト（Apple, Banana, Cherry）を `IReadOnlyList<SalesRecord>` として返します。

#### 3.3. フォーマットの動的選択と整形（Formatters層の呼び出し）

* **コードポインタ**: `SolidSample.Good\Services\ReportService.cs` 内の `BuildReport` メソッド -> `SolidSample.Good\Formatters\CsvFormatter.cs` の `Format(...)`
* **プロセスの振る舞い**:
  1. 注入されているフォーマッターのリスト（`_formatters`）から、`FirstOrDefault` を使って `FormatName` が `"CSV"` に一致するものを**動的に検索・選択**します。これにより、`if/else` 分岐を使うことなく処理対象を決定できます（OCP違反の回避）。
  2. 見つかった `CsvFormatter` インスタンスの `Format(records)` メソッドを呼び出します。
  3. `CsvFormatter` 内部で `StringBuilder` を用いて「Product,Amount」のヘッダーが付いたCSV形式の文字列が組み立てられ、`ReportService` に返されます。

#### 3.4. データの出力（Output層の呼び出し）

* **コードポインタ**: `SolidSample.Good\Services\ReportService.cs` 内の `PrintToConsole` メソッド -> `SolidSample.Good\Output\ConsoleWriter.cs` の `Write(string content)`
* **プロセスの振る舞い**:
  * `BuildReport` から返ってきたCSV文字列（`content`）を受け取ります。
  * `_consoleWriter.Write(content)` を呼び出し、具象クラスである `ConsoleWriter` が `Console.Write(content)` を実行して画面にCSVレポートを出力します。

### 別のユースケース（ファイル保存、メール送信）での変化

`SaveToFile("JSON", filePath)` や `SendByEmail("CSV", "user@example.com")` が呼ばれた場合も、基本的な流れ（**3.2 データ取得** と **3.3 フォーマット選択**）は全く同じ `BuildReport` メソッドを通ります。

最後のステップだけが、それぞれの役割に特化した小さなインターフェース（ISPの遵守）に基づいて切り替わります。

* `SaveToFile` の場合: `_fileWriter.Write(filePath, content)` が呼ばれ、`FileWriter.cs` を通じて物理ファイルに書き込まれます。
* `SendByEmail` の場合: `_emailSender.Send(to, "Sales Report", content)` が呼ばれ、`SmtpEmailSender.cs` を通じて擬似的なメール送信ログが出力されます。

### プロセス解析のまとめ

Goodパターンの実行プロセスにおいて、中心にいる `ReportService` は「どこからデータを取って」「どの具象クラスで変換し」「どこに物理出力するか」の具体的な詳細を一切知りません。

コンストラクタで受け取った「インターフェース（抽象という名の契約）」のメソッドを順番に呼び出すという「全体の流れの調整（オーケストレーション）」だけに専念しているため、非常に変更に強く、テストがしやすい理想的な実行プロセスが実現されています。
