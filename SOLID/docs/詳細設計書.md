# レポート出力システム 詳細設計書（コードポインタ対応版）

## 1. システム概要

本システムは、SOLID原則を学ぶ研修用のサンプルアプリケーションです。業務で頻出する「売上データを取得 → フォーマット(CSV/JSON/Markdown)に整形 → 出力先(コンソール/ファイル/メール)に届ける」という一連の処理を実装しています。同一の要件に対し、意図的に原則に違反した「Badパターン」と、原則を適用した「Goodパターン」の2つを用意し、設計の違いを比較できるように構成されています。

---

## 2. Badパターン設計（アンチパターンの実装）

すべての処理を単一のクラスに詰め込み、SOLIDの全原則に違反する設計となっています。機能追加のたびに既存のコードを修正する必要があり、テストも困難です。

### 2.1 エントリーポイント

* **コードポインタ**: `SolidSample.Bad\Program.cs`
* **解説**: Badパターンの実行フローを定義しています。`ReportManager`を直接インスタンス化し、正常系ケースと例外を発生させる異常系ケース（LSP違反の確認）を呼び出します。

### 2.2 Godクラス（全責務の集中）

* **コードポインタ**: `SolidSample.Bad\ReportManager.cs`
* **解説**: データ取得、フォーマット整形、出力先分岐のすべてのロジックを1つのメソッド（`GenerateAndDeliverReport`）に詰め込んでいます。
* **SOLID原則違反のポイント**:
  * **SRP（単一責任）違反**: ダミーデータ生成、整形、出力のロジックが1箇所に集中しています。
  * **OCP（開放閉鎖）違反**: フォーマットや出力先の分岐が`if / else if`でハードコードされており、拡張に対して閉じています。
  * **LSP（リスコフ置換）違反**: `format`が"PDF"かつ`outputTarget`が"Console"の場合に`NotSupportedException`をスローし、親の契約を破る処理が含まれています。
  * **DIP（依存関係逆転）違反**: `_connectionString`や`_smtpServer`といった設定値や外部リソースの概念がクラス内に直接ハードコードされています。

---

## 3. Goodパターン設計（クリーンアーキテクチャへの適用）

SOLIDの5原則をすべて遵守し、責務ごとにクラスとインターフェースを細かく分割した設計です。

### 3.1 エントリーポイントとComposition Root (DI)

* **コードポインタ**: `SolidSample.Good\Program.cs`
* **解説**: アプリケーションの起動地点であり、DIコンテナ（`ServiceCollection`）を用いて具象クラスの組み立てをここでのみ行います。
* **SOLID適用**: 新しいフォーマットを追加する際は、このファイルのDI登録を1行追加するだけで済むため、OCPを遵守しています。

### 3.2 ドメイン層 (Domain)

* **コードポインタ**: `SolidSample.Good\Domain\SalesRecord.cs`
* **解説**: 商品名（Product）と売上金額（Amount）を保持する単一の責務を持つ`record`型です。

### 3.3 データアクセス層 (DataAccess)

* **抽象コードポインタ**: `SolidSample.Good\DataAccess\ISalesRepository.cs`
* **具象コードポインタ**: `SolidSample.Good\DataAccess\InMemorySalesRepository.cs`
* **解説**: 売上データを取得する責務を担います。
* **SOLID適用**: インターフェース（ISP）を定義し、最小限のメソッドのみを持たせることで上位層との依存関係を逆転（DIP）させています。

### 3.4 フォーマット層 (Formatters)

* **抽象コードポインタ**: `SolidSample.Good\Formatters\IReportFormatter.cs`
* **具象コードポインタ**:
  * `SolidSample.Good\Formatters\CsvFormatter.cs`
  * `SolidSample.Good\Formatters\JsonFormatter.cs`
  * `SolidSample.Good\Formatters\MarkdownFormatter.cs`
* **解説**: 取得したデータを文字列に整形する拡張ポイントです。
* **SOLID適用**: 新しいフォーマットが必要になった場合は既存コードを触らずに具象クラスを追加するだけで済む（OCP）構造です。また、どの実装も例外を投げずに文字列を返すためLSPを満たしています。

### 3.5 出力層 (Output)

* **インターフェース分割コードポインタ**:
  * `SolidSample.Good\Output\IConsoleWriter.cs`
  * `SolidSample.Good\Output\IFileWriter.cs`
  * `SolidSample.Good\Output\IEmailSender.cs`
* **具象コードポインタ**: `ConsoleWriter.cs`, `FileWriter.cs`, `SmtpEmailSender.cs`
* **解説**: データを適切な出力先に届ける責務を担います。
* **SOLID適用**: 巨大な`IReport`インターフェースを作るのではなく、書き込み先の特性に応じた小さなインターフェースに分割（ISP）しています。

### 3.6 サービス層 (Services)

* **コードポインタ**: `SolidSample.Good\Services\ReportService.cs`
* **解説**: データ取得・整形・出力を連携させる調整役となるクラスです。
* **SOLID適用**: 自身の内部で`new`キーワードを使わず、コンストラクタ経由ですべての依存（抽象）を受け取ることでDIPを遵守しています。

## 4. テスト設計によるSOLIDの恩恵

具象クラスから抽象（インターフェース）に依存を切り替えたことで、単体テストが容易になる構造を実現しています。

* **サービス層のテスト**: `SolidSample.Tests\ReportServiceTests.cs`
  * **解説**: 実際のDBやファイルシステム、SMTPサーバーを使用せず、`Moq`ライブラリを用いて`ISalesRepository`や各Writerのモックを注入しています。これにより、外部リソースの状態に依存せず純粋なビジネスロジック（調整処理）のみをテストできています。

* **出力・整形ロジックの個別テスト**: `SolidSample.Tests\OutputTests.cs`, `SolidSample.Tests\ReportFormatterTests.cs`
  * **解説**: SRPにより各クラスの責務が単一化されたため、CSVが正しく整形されているか、またはConsoleに正しく文字列が渡されているかなど、小さな単位で独立したテストが記述されています。
